# Recovery/backup CLI 1.0 reliability benchmark

**Research date:** 2026-07-18
**Purpose:** background evidence for evaluating a recovery/backup CLI 1.0. This note describes reliability requirements and established product patterns; it does not choose this project's audience, scope, storage model, or product positioning.

## Source methodology

- Sources are limited to primary material: official product documentation, official source repositories where documentation points to implementation details, NIST/CISA publications, and POSIX. Secondary reviews and vendor comparison blogs were excluded.
- Product observations use the official stable documentation available on the research date: restic 0.19.1, Borg 1.4.4, the current Kopia documentation, and current Apple Time Machine support documentation. Time Machine is included as a disaster-recovery UX benchmark, not as a CLI peer.
- A documented feature is evidence of an established pattern, not independent proof that every implementation and backend behaves correctly. “Not documented” below means only that the reviewed public documentation does not make the guarantee.
- **Must-have 1.0** means the minimum needed to make a credible, testable recovery claim. Repository-specific requirements apply only if 1.0 owns backup storage. **Advanced/post-1.0** means valuable defense-in-depth, scale, automation, or repair behavior that can follow without making the basic restore path unsafe.

## Standards-derived baseline

The strongest baseline is not “a backup command ran”; it is “the required data can be recovered to a known state, within declared boundaries, and the result can be trusted.”

- NIST SP 800-53 Rev. 5.1 CP-9 ties backup frequency to recovery time and recovery point objectives, requires protection of backup confidentiality, integrity, and availability, calls for periodic reliability/integrity tests, and separately calls for restoration tests using samples. CP-10 requires recovery to a known state and identifies rollback/journaling for transaction-based systems. These controls make a useful distinction between media/object verification and functional restore testing. [NIST SP 800-53 Rev. 5.1, CP-9 and CP-10](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)
- CISA recommends offline, encrypted backups and regular testing of both availability and integrity in a disaster-recovery scenario; it also warns that ransomware commonly tries to delete or encrypt accessible backups. [CISA #StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide)
- NIST's ransomware recovery practice guide emphasizes that recovery must restore trust in the accuracy of recovered data and that auditing/reporting supports recovery and investigation. [NIST SP 1800-11](https://csrc.nist.gov/pubs/sp/1800/11/final)
- For a local filesystem, POSIX requires directory mutations such as rename to be atomic and serializable, but the rationale explicitly notes that atomicity does not itself guarantee durability. A tool therefore needs to distinguish “no partial pathname was exposed” from “bytes are durable after power loss,” and it cannot assume the same guarantee across filesystems. [POSIX.1-2024 directory operations](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap04.html), [POSIX rationale](https://pubs.opengroup.org/onlinepubs/9799919799/xrat/V4_xbd_chap01.html)

## Must-have 1.0 benchmark

### 1. A restore result must be unambiguous

A 1.0 restore should require or resolve to an immutable backup identifier, show the source and destination before writing, support restoring a subset, and finish with a machine-checkable summary of restored, skipped, overwritten, and failed items. “Latest” is useful convenience, but the resolved ID and time should be printed and recorded. Restic and Kopia expose explicit target and overwrite controls; Borg's warning that extraction uses the current directory demonstrates why an implicit target is a recovery risk. [restic restore](https://restic.readthedocs.io/en/stable/050_restore.html), [Kopia restore](https://kopia.io/docs/reference/command-line/common/restore/), [Borg extract](https://borgbackup.readthedocs.io/en/stable/usage/extract.html)

Destructive reconciliation—deleting destination files not present in the backup—must never be implicit. It needs a dry-run, an explicit flag, a bounded target, and output that identifies every deletion. Existing tools make overwrite common, but their defaults are not a sufficient safety specification: restic defaults to overwrite and guards broad `--delete`; Kopia defaults to overwriting several entry types and exposes separate controls. [restic restore safety](https://restic.readthedocs.io/en/stable/050_restore.html#deleting-files-not-in-snapshot), [Kopia restore flags](https://kopia.io/docs/reference/command-line/common/restore/)

### 2. Interruption must not create a false success

There are two different atomicity boundaries:

1. **Backup publication:** a backup/snapshot must not become selectable as complete until all referenced content and metadata are durably reachable. Interrupted work may remain as garbage or a clearly incomplete checkpoint, but it must not look restorable. Restic's pack → index → snapshot ordering and Borg's commit records are mature examples. [restic ordering](https://restic.readthedocs.io/en/stable/100_references.html#read-and-write-ordering), [Borg transactions](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)
2. **Restore publication:** each output file must either remain the old version or become the fully written, validated new version; an interruption must not expose a truncated file as complete. A same-filesystem temporary file plus atomic rename is the normal local pattern, with optional syncing when power-loss durability is promised. POSIX does not provide an atomic cross-filesystem rename, and atomic namespace change alone is not durability. Kopia makes this boundary explicit with `--write-files-atomically`; restic explicitly warns that in-place interruption can leave partial files. [POSIX `rename`](https://pubs.opengroup.org/onlinepubs/9799919799/functions/rename.html), [Kopia restore](https://kopia.io/docs/reference/command-line/common/restore/), [restic restore](https://restic.readthedocs.io/en/stable/050_restore.html#restoring-in-place)

Whole-tree atomic restore is not a universal 1.0 requirement; it is often impossible without filesystem snapshots or a final directory swap. The 1.0 requirement is a declared boundary, no false success, safe rerun, and a precise partial-results report.

### 3. Verification must cover both structure and bytes

A 1.0 that owns stored backups needs a read-only verification command with at least two explicit scopes:

- **Structural:** every selectable snapshot/manifest resolves to all required metadata and content objects; indexes agree with stored objects.
- **Content:** stored bytes are read and authenticated/hashed, not merely checked for object existence.

The command must clearly report which scope ran, how much data was covered, its cost implications, and a nonzero result for any unverifiable item. restic, Borg, and Kopia all distinguish inexpensive structural checks from full data reads; Kopia explicitly says a successful test restore remains the gold standard. [restic checks](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#checking-integrity-and-consistency), [Borg checks](https://borgbackup.readthedocs.io/en/stable/usage/check.html), [Kopia consistency](https://kopia.io/docs/advanced/consistency/)

An automated sampled-restore scheduler can be post-1.0, but 1.0 must leave a runnable restore-drill procedure. NIST treats integrity testing and sample functional restoration as separate controls; passing one cannot be reported as passing the other. [NIST SP 800-53 CP-9](https://csrc.nist.gov/pubs/sp/800/53/r5/upd1/final)

### 4. Security properties must be explicit and fail closed

If 1.0 owns a repository or sends backups to storage outside the source machine, it needs authenticated encryption for content **and metadata**, a password/key derivation scheme intended for human secrets, non-interactive secret input that avoids command-line arguments, and no secret material in logs or structured output. A wrong password or failed authentication must stop before destination writes. restic, Borg, and Kopia all authenticate stored content under a stated threat model. [restic encryption](https://restic.readthedocs.io/en/stable/100_references.html#keys-encryption-and-mac), [Borg security](https://borgbackup.readthedocs.io/en/stable/internals/security.html), [Kopia encryption](https://kopia.io/docs/advanced/encryption/)

The UX must state what the protection does **not** cover: loss of the password/key can make data unrecoverable; encryption does not prevent an authorized or compromised client from deleting the repository; and a compromised source can back up already-corrupted data. CISA's offline-backup recommendation and the restic/Borg threat models are explicit about the deletion gap. [CISA](https://www.cisa.gov/stopransomware/ransomware-guide), [restic threat model](https://restic.readthedocs.io/en/stable/100_references.html#threat-model), [Borg threat model](https://borgbackup.readthedocs.io/en/stable/internals/security.html#attack-model)

If 1.0 delegates storage entirely to another backup engine, it may delegate cryptography too, but it must surface that engine's verification and credential failures accurately rather than implying independent protection.

### 5. Retention must be previewable and scoped

If 1.0 creates continuing backup history, it needs at least a simple bounded retention rule, deterministic selection, and a dry-run that shows kept and removed recovery points. Retention must be scoped by backup set/source so one machine or path cannot accidentally age out another. Logical removal should be distinguishable from irreversible physical reclamation where the storage model permits it. restic groups policy decisions by host/path and separates forget from prune; Borg strongly recommends dry-run/list and separates prune from compaction. [restic retention](https://restic.readthedocs.io/en/stable/060_forget.html), [Borg retention](https://borgbackup.readthedocs.io/en/stable/usage/prune.html)

Complex GFS calendars, tags, legal hold, and cost-aware storage-class policies can wait. A 1.0 without automated retention can still be credible only if repository growth and manual deletion are explicitly bounded and observable; silently filling the backup destination is a recovery failure mode, not merely an operations inconvenience.

### 6. Failure behavior must preserve evidence

Expected failures—source read changes/errors, destination full, network interruption, lock contention, wrong credentials, unsupported metadata, and corrupted objects—need distinct nonzero outcomes. Partial source reads must not be labeled a complete successful backup. Warnings that reduce fidelity must be distinguishable from success and from fatal failure; restic and Borg both publish this distinction in their exit contracts. [restic exit codes](https://restic.readthedocs.io/en/stable/075_scripting.html#exit-codes), [Borg return codes](https://borgbackup.readthedocs.io/en/stable/usage/general.html#return-codes)

The safe 1.0 recovery path is diagnose first, mutate second: verification is read-only; stale locks can be inspected and cleared deliberately; an interrupted operation is rerunnable; repair is never silently coupled to normal backup or restore. Borg's strong repair warnings and Kopia's advice to preserve possibly useful cache state are good precedents. [Borg repair warning](https://borgbackup.readthedocs.io/en/stable/usage/check.html#about-repair-mode), [Kopia corruption guidance](https://kopia.io/docs/advanced/consistency/)

Repository salvage, index reconstruction, erasure-code repair, and resumable transfer checkpoints are advanced. They should not displace the simpler 1.0 guarantee that ordinary interruption cannot publish a bad recovery point.

### 7. Observability is part of correctness

A reliable CLI needs stable exit semantics, human-readable stderr diagnostics, a concise stdout success result, and machine-readable output for automation. At minimum, final output should include operation type, resolved backup ID, start/end time, files and bytes considered/written/skipped/failed, verification scope, and a stable error category. Long operations should expose progress without making parsers consume terminal formatting. restic's JSONL messages and “unknown exit code means failure” rule, and Borg's success/warning/error split, are strong precedents. [restic scripting](https://restic.readthedocs.io/en/stable/075_scripting.html), [Borg general behavior](https://borgbackup.readthedocs.io/en/stable/usage/general.html)

Metrics exporters, dashboards, notification integrations, and long-term operation history are post-1.0. A structured final result and dependable exit status are not.

### 8. Portability requires declared fidelity, not silent degradation

A 1.0 must publish a supported OS/filesystem matrix and define which entry types and metadata it captures and restores: regular files, directories, symlinks, hard links, ownership, modes/ACLs, timestamps, xattrs, flags, sparse layout, and special files as applicable. On an incompatible target it should restore what it safely can, report every fidelity loss, and return a documented warning/partial status. restic and Borg both document platform privilege and metadata limitations rather than claiming universal equivalence. [restic metadata limits](https://restic.readthedocs.io/en/stable/050_restore.html), [Borg metadata support](https://borgbackup.readthedocs.io/en/stable/usage/general.html#support-for-file-metadata)

Repository or manifest formats need an explicit version. New software must either read old 1.0 recovery points or refuse safely with an actionable version message; migrations must be explicit and must not destroy the only readable copy. restic makes format upgrades explicit because they raise the minimum reader version, while Kopia promises backward reads, refuses unsafe mutation, and never auto-upgrades. [restic format upgrade](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#upgrading-the-repository-format-version), [Kopia compatibility](https://kopia.io/docs/advanced/compatibility/)

Perfect cross-OS metadata round-tripping and application-consistent snapshots of live databases are advanced unless selected as explicit product scope. A 1.0 must still disclose its consistency boundary and must not silently claim a coherent point-in-time image when source files changed during capture.

### 9. Disaster recovery must work from a blank-enough machine

The shortest credible drill is: obtain an authentic compatible binary, provide repository location and recovery secret, list recovery points, inspect/select one, restore to an explicit target, and verify the result. These steps need to be documented without depending on local cache or the original configuration directory. Kopia's reconnect token is an advanced convenience, but its warning that an embedded password grants full repository access is the right security posture; Time Machine's guided Recovery/Migration Assistant flow is the consumer UX benchmark. [Kopia reconnect](https://kopia.io/docs/reference/command-line/), [Apple full recovery](https://support.apple.com/en-euro/guide/mac-help/mh15638/mac)

The 1.0 documentation should include a printable/offline recovery checklist and make unrecoverable dependencies—password, key file, backend credentials, minimum compatible version—visible during setup. Browse mounts, GUIs, remote recovery orchestration, and automatic bare-metal rebuilding can follow.

## Advanced/post-1.0 patterns

These patterns materially improve resilience but are not substitutes for the 1.0 fundamentals above:

- Immutable/object-locked or append-only storage, restricted delete credentials, point-in-time repository access, and offline copies. Kopia documents object locks and restricted credentials; CISA recommends offline encrypted copies. [Kopia ransomware protection](https://kopia.io/docs/advanced/ransomware-protection/), [CISA](https://www.cisa.gov/stopransomware/ransomware-guide)
- Scheduled sampled/full verification and automated restore drills with coverage history, alerts, and RPO/RTO reporting.
- Whole-tree atomic cutover using filesystem snapshots, staging volumes, or transactional deployment integration.
- Application-aware quiescing and restore hooks for databases, VMs, and service dependency order.
- Repair/salvage tooling: index rebuilds, lost-manifest discovery, erasure coding, repository rollback, and forensic export. Repair must remain separate from read-only diagnosis.
- Distributed concurrency, multi-client authorization, dual control for destructive operations, centralized repository servers, quotas, and multi-tenant audit.
- Rich browse/mount/GUI flows, bandwidth scheduling, storage classes, repository replication/synchronization, and cross-repository copy.

## Minimal acceptance evidence for a credible 1.0 claim

The following checks are implementation-neutral and test the benchmark rather than a particular architecture:

1. Corrupt one metadata object and one content object; structural and full verification detect the appropriate failures, and restore never reports success.
2. Interrupt backup before content write, between content and metadata, and just before final publication; no interrupted run appears as a complete recovery point, and rerunning is safe.
3. Interrupt restore during a large file and during metadata application; no truncated file is presented as complete, the exit is nonzero, partial work is reported, and rerunning converges.
4. Exercise destination-full, read-only target, transient network failure, stale lock, wrong password, and source-read error; each is distinguishable in human and machine output.
5. Restore representative supported metadata and entry types on every supported platform; unsupported fidelity is reported, not silently discarded.
6. Compare retention dry-run selection with actual selection, scope it across multiple backup sets, and prove that the last valid recovery point is not silently reclaimed.
7. Start from a clean user profile or second machine and complete the documented list → select → restore → verify drill using only declared recovery dependencies.

The benchmark's central inference is that **restore correctness, commit safety, and evidence must underpin any 1.0 reliability claim**. Deduplication, compression, broad backend support, and sophisticated retention are valuable, but none can compensate for a recovery point that is ambiguous, unverifiable, partially published, or inaccessible during a real disaster.
